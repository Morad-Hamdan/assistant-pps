1.  PR├ëSENTATION DU PROJET
================================================================================

L'Assistant PPS est une application web de pilotage RH qui permet de :

  - Lire un fichier Excel (recap.xlsx) contenant la liste des employ├®s et leurs
    certifications PPS (Pratiques Professionnelles S├®curit├®)
  - Migrer ces donn├®es dans une base SQLite
  - Calculer automatiquement le statut de chaque certification PPS :
      * VALIDE   : date de moins de 2,75 ans
      * A REQUALIFIER : date entre 2,75 et < 2,9589 ans
      * PREVU    : date entre 2,9589 et 3 ans
      * SUSPENDU : date de plus de 3 ans
      * EN COURS : pas de date mais valeur "EC" dans l'Excel
      * NON APPLICABLE : pas de date du tout
  - Visualiser ces donn├®es via un tableau de bord interactif
  - Filtrer, chercher, explorer les employ├®s et leurs PPS
  - Authentifier les utilisateurs (admin / employee)

Exemple de r├©gle m├®tier :
  Un employ├® a pass├® son PPS "Soudure" le 22/03/2018.
  Aujourd'hui, cela fait plus de 3 ans. Le statut est donc "suspendu".
  Si la case Excel contient "VALIDE" mais la date est ancienne, l'application
  d├®tecte une incoh├®rence et l'enregistre dans le rapport de correction.

C'est un syst├©me 100% r├©gles-m├®tier (pas d'IA, pas de LLM). Toute la logique
est dans le fichier migrate_excel_to_sqlite.py avec la fonction compute_statut().

L'architecture choisie est une architecture 3-tiers avec s├®paration front/back :

    └─────────────┘              └──────────────┘             └──────────┘

Pourquoi FastAPI + Laravel et pas un seul langage ?
----------------------------------------------------
1. FASTAPI (Python) :
   - Excellente biblioth├¿que Pandas pour lire les Excel (.xlsx)
   - openpyxl pour manipuler les cellules Excel
   - sqlite3 (int├®gr├® ├  Python) pour la base SQLite
   - Syntaxe claire pour les API REST
   - Parfait pour la couche donn├®es + logique m├®tier

2. LARAVEL (PHP) :
   - Moteur de templating Blade puissant (vues HTML)
   - Syst├¿me d'authentification int├®gr├® (Auth::attempt, sessions)
   - Middleware pour la s├®curit├® (CheckRole)
   - Syst├¿me de migrations et seeders pour la base utilisateurs
   - Excellent pour le rendu HTML / dashboard

3. SQLITE :
   - Pas besoin d'installer un serveur de base de donn├®es
   - Un seul fichier .db, facile ├  transporter
   - Suffisant pour un volume de donn├®es RH (quelques centaines d'employ├®s)

4. Pourquoi pas un framework full-stack unique ?
   - Laravel seul : lecture Excel compliqu├®e (pas de pandas)
   - Python seul (Django/Flask) : pas de Blade, pas d'auth int├®gr├®e aussi simple
   - Avec cette s├®paration, chaque langage fait ce qu'il fait de mieux

C'est ce qu'on appelle une architecture "d├®coupl├®e" : on peut changer le

LES POINTS CL├ëS DE LA DIFF├ëRENCE :

EXEMPLE CONCRET :

       -> Lire un Excel n├®cessite PhpSpreadsheet (plus lourd que Pandas)

C'est ce qu'on appelle le "polyglot programming" (programmation multilingue).

──── 5.2 services/database.py ──────────────────────────────────────────────────
Fichier : backend/services/database.py (209 lignes)

C'est le fichier LE PLUS IMPORTANT du backend. Il contient TOUTE la logique
m├®tier et l'acc├¿s aux donn├®es.

Fonctions :

a) get_connection() -> sqlite3.Connection
   - Cr├®e une connexion ├á la base SQLite

   - Active le mode WAL (Write-Ahead Logging) pour les performances
   - Active les foreign keys (contrainte d'int├®grit├® r├®f├®rentielle)
   - Configure row_factory = sqlite3.Row pour acc├®der aux colonnes par nom

   Note technique : row_factory permet d'├®crire row["nom"] au lieu de row[1].
   C'est plus lisible et moins fragile (si l'ordre des colonnes change).

b) init_schema()
   - Cr├®e les tables si elles n'existent pas (CREATE TABLE IF NOT EXISTS)
   - Table "employees" : matricule (UNIQUE), nom, prenom, processus, uap, eap

     statut, raw_value
   - Cr├®e des indexes pour acc├®l├®rer les recherches (employee_id, statut, pps_name)

   Pourquoi des indexes ? Sans index, une recherche sur 10 000 enregistrements
   parcourt TOUTE la table (full scan). Avec l'index, c'est instantan├® (log(n)).

c) get_all_employees() / get_employee_by_matricule() / get_employee_by_name()
   Fonctions CRUD simples : SELECT avec ou sans filtre.

d) get_pps_assignments(employee_id) / get_pps_by_name(pps_name)
   R├®cup├©re les affectations PPS pour un employ├® ou un nom de PPS.

e) get_all_distinct_pps_names()
   Retourne la liste de tous les PPS distincts (pour les menus d├®roulants).

f) build_employee_dataset() (la fonction la plus complexe)
   C'est le c┼"ur du projet. Elle construit un "dataset" complet ├á partir des
   deux tables (employees + pps_assignments).

   Algorithme :
   1. Pour chaque employ├® dans la table employees :
   2.   R├®cup├¿re toutes ses affectations PPS
   3.   Pour chaque affectation, lit le statut et classe le PPS dans la bonne
        liste (valide / requalifier / prevu / suspendu / en_cours)
   4.   Compte le nombre de PPS par statut
   5.   Calcule 2 scores :
        - strict_score : pourcentage de PPS valides parmi les PPS applicables
        - operational_score : pourcentage (valides + requalifier + prevu)
   6.   D├®termine le risque :
        - "ALERTE" si au moins 1 PPS suspendu (danger)
        - "SURVEILLANCE" si requalifier ou prevu (attention)
        - "" sinon (vert)
   7.   Retourne un dictionnaire complet pour chaque employ├®

   Exemple de donn├®es retourn├®es pour un employ├® :
   {
     "matricule": "12345",
     "name": "DUPONT Jean",
     "valid": 5,           # 5 PPS valides

     "suspended": 1,       # 1 suspendu (ALERTE !)
     "prevu": 0,
     "en_cours": 1,
     "valid_pps": ["PPS 001", "PPS 002", ...],
     "suspended_pps_dates": [
       {"pps": "PPS 012", "date": "2018-03-22"}

   }

g) get_dataset_meta()

   colonnes, distribution des statuts, ├®chantillon de donn├®es.

   Utile pour les cartes stats du dashboard.

──── 5.3 services/qualification_engine.py ──────────────────────────────────────
Fichier : backend/services/qualification_engine.py (17 lignes)

Petit fichier utilitaire pour la normalisation de texte.

Fonction normalize_text(text) :
  - Utilise unicodedata.normalize('NFKD', text) pour d├®composer les caract├¿res

  2. D├®tection automatique des colonnes de dates :

7.  LOGIQUE M├ëTIER : LE CALCUL DES STATUTS PPS
================================================================================

C'est la partie la plus importante du projet ├á comprendre.

Le fichier recap.xlsx contient pour chaque employ├® :
  - Ses infos : matricule, nom, pr├®nom, processus, uap, eap
  - Des colonnes de dates : "Date PPS XXX" avec la date de validation

Le calcul du statut se fait dans compute_statut() (migrate_excel_to_sqlite.py) :

    ├ëtat 1 : Pas de date du tout

        -> Si elle contient "EC" (En Cours) : statut = "en_cours"

           Date PPS        ├ége      Statut

           2023-07-22    2.92 ans   prevu        (>= 2.9589)
           2022-06-20    3 ans      suspendu     (> 3 ans)

cr├®e une incoh├®rence (enregistr├®e dans rapport_correction_pps.txt).
